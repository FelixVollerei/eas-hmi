# 历史读取与完整性边界（0.1.1）

0.1.0 的 history/diff/events 在 `_recover()` 已校验投影后，仍调用 `_chain()` 反序列化并校验每份历史模型。若每份模型为 S 字节、共有 R 条提交，常规读约为 O(R×S)，还会重复执行 Pydantic 验证与语义摘要。空 watch 也走这条路径。

0.1.1 保留原格式、不可变快照提交和唯一的 HEAD 原子边界，已存在工程无需迁移。

| 路径 | 当前行为与复杂度 |
|---|---|
| 当前模型 | 校验 HEAD 指向的完整提交，验证 SHA256、身份、revision、模型及语义 hash |
| history --limit N | 校验两份 JSONL 投影摘要，复用读入的字节，仅解析末 N 条 operation；O(S+J+返回数据)，J 为两份投影总字节数 |
| diff --revision / 最新 | 同上，只解析所需 revision 对应的一条 operation；不会反序列化以前的模型 |
| events --since-revision | 无新 revision 时仅校验当前提交，O(S)；有新 revision 时校验投影，只解析游标之后的 operation，再生成相同事件结构 |
| watch 空轮询 | 每次仍读取并验证当前模型，不读历史提交或投影；CLI 启动默认游标时额外有一次 load，不是零 I/O |
| 正常提交 | 验证当前模型与父投影后，用当前 operation/events 更新投影，不重扫所有历史模型；JSONL 仍整文件原子重写 |
| 投影缺失/损坏、提交后崩溃恢复 | 从完整提交链校验并重建投影；仍为 O(R×S)，属于慢路径 |
| history --audit | 强制检查全部历史提交与父子 hash/revision 关系，检测休眠旧提交的损坏；明确为 O(R×S) |

普通历史读校验“当前权威提交 + 对应该 HEAD 的完整投影摘要”，不再每次重新审计每个旧模型。这与旧版 load 的投影快路径一致，但与旧版 history 的全链检查不同；需要历史介质完整性检查时必须显式 `--audit`。摘要防意外损坏，不防能同时修改模型、HEAD 和校验值的特权编辑者。

读取仍加 OS 文件锁；读者、写者和恢复相互串行化。空 events 不修复历史投影，因为本次没有历史数据返回；下一次 load/history/有增量 events 会检测并恢复。投影的同长度内容篡改也通过摘要检出，并有回归测试。

**没有解决的规模问题**：每个 commit 仍保存全模型，磁盘约 O(R×S)；投影读校验与提交重写仍随 J 增长，全量 history/events 的返回体必然随历史增长。没有称为分段索引、增量快照或长期存储方案。若进入数万次提交或更大模型，需要后续做日志分段索引、checkpoint+delta、显式审计策略和恢复上界设计，再重新故障注入验收，不能靠本轮 107 提交实测外推。

本轮使用独立合成目录、同一解释器与同一输入，对 Git 交付基线及当前代码作交替测量，包含进程启动与输出；原始样本及失败在 `build/review/history*/performance.json`。p95 采用 nearest-rank；10 个样本时 p95 等于最大值。不是冷盘测试，也不是 Agent token 比较。实测汇总见 [复核报告](review-corrections.md)。
